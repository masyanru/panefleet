== PRODUCT ==

*Summary:* Add a configurable setting in the TUI settings file that selects which key starts voice input in the TUI, mirroring the GUI's "key for activating voice input" (`VoiceInputToggleKey`) setting. The setting defaults to `None` (no keybinding). The set of selectable keys is the GUI's option list filtered by what the TUI's crossterm input layer can actually deliver. The TUI keeps its existing tap-to-start interaction model (press to start, Escape/Enter to stop); GUI-style hold-to-toggle (push-to-talk) is explicitly out of scope for this change and recorded as future work.

*Key design choices:*
1. **Tap-to-start, not hold-to-toggle.** The TUI's voice model is already tap-to-start (`crates/warp_tui/src/voice_input.rs:79` start / `:127` stop). We reuse it. A faithful hold-to-toggle mirror would require enabling `REPORT_EVENT_TYPES` + handling key `Release` events in the shared input layer and would only work on a subset of terminals — too risky and too large for this estimate. See *Design alternatives* (A vs B).
2. **Reuse the GUI's `VoiceInputToggleKey` enum as a new TUI-surface setting.** Same TOML value space and path (`agents.voice.voice_input_toggle_key`) so configs are portable, but `surface: SettingSurfaces::TUI` so it only appears in / is read from the TUI's `settings.toml`. Default `None`.
3. **Map `KeyCode::Modifier(_)` in the TUI input-conversion layer.** Today bare-modifier presses are dropped (`crates/warpui_core/src/runtime/event_conversion.rs:165`), which is the only reason the GUI's standalone-modifier options can't fire in the TUI. Mapping them to a `KeyDown` keystroke (press only) makes Alt/Control/Shift — and Super, best-effort — deliverable. `Fn` is excluded (no crossterm `KeyCode`). No `REPORT_EVENT_TYPES`, no `Release` handling in this PR.

*Behavior* (numbered, testable invariants from the user's view):
1. **Default is off.** With no `agents.voice.voice_input_toggle_key` in the TUI settings file (or set to `none`), no key starts voice input in the TUI. The previously hardcoded `ctrl-s` default no longer starts voice input. The binding *name* `tui:session:start_voice_input` still exists (so `/voice` and future `keybindings.yaml` overrides keep working); it simply has no keystroke attached.
2. **Configured key starts voice (tap).** When the setting is a supported modifier (e.g. `control_left`), pressing that bare modifier alone in the session composer starts voice input (enters the `Listening` state), sourced as `VoiceInputStartSource::Keybinding`. Repeated presses while already listening are ignored (the existing `is_active` guard).
3. **Stop is unchanged.** While voice is listening, the existing stop controls apply — Escape cancels, Enter submits/stops — exactly as today. Releasing the configured key does nothing (no hold-to-toggle in this PR).
4. **Feasibility-filtered options.** The selectable options are the GUI's `VoiceInputToggleKey` variants filtered by TUI feasibility: `None`, `AltLeft`/`AltRight`, `ControlLeft`/`ControlRight`, `ShiftLeft`/`ShiftRight`, `SuperLeft`/`SuperRight` (best-effort). `Fn` parses (it's a variant of the reused enum) but maps to no active binding — it is documented as unsupported in the TUI. `Super` is documented as unreliable (many terminals do not forward ⌘/Super).
5. **Graceful degradation.** On terminals that do not report bare-modifier presses (no Kitty keyboard enhancement, or a terminal that swallows Super), the configured binding simply does not fire — no crash, no swallowed input, no interference with chords or other bindings.
6. **No interference with chords.** Pressing a modifier as part of a chord (e.g. `ctrl-s`, `ctrl-c`, `ctrl-v`) does not start voice input unless the standalone modifier alone is the configured key *and* it is pressed alone. Chord events arrive as combined `KeyDown` events (key + modifiers), not as a bare-modifier `KeyDown`, so they do not match the standalone-modifier voice binding.
7. **Back-compat.** The `tui:session:start_voice_input` binding name and its `TUI_BINDING_GROUP` ownership are preserved; only its default keystroke changes (from hardcoded `ctrl-s` to setting-driven, default none). The TUI binding validators still pass.

*Design alternatives* (per decision point with more than one reasonable approach):

- **Interaction model — hold-to-toggle (A) vs tap-to-start (B).**
  - (A) Faithful hold-to-toggle mirror: enable `REPORT_EVENT_TYPES`, handle `KeyEventKind::Release`, map `KeyCode::Modifier(_)`, wire press→start / release→stop, gate by `keyboard_enhancement_supported`. Closest to the GUI. Pros: parity with GUI push-to-talk. Cons: touches the shared input layer more invasively (Release handling changes event flow for every key); only works on terminals that report release events; Super/Fn likely never work; pushes scope toward L; release events can race with focus changes (the GUI itself notes this at `voice.rs:240-250`). 
  - (B) Tap-to-start with a configurable key (chosen): add the TUI setting, wire the chosen key to the existing `StartVoiceInput` tap action, map `KeyCode::Modifier(_)` Press→`KeyDown` only. Pros: reliable (no release dependence), contained, fits M, reuses the existing TUI voice lifecycle, degrades gracefully. Cons: does not replicate GUI *hold* semantics — a tap starts voice and Escape/Enter stops it (not release-to-stop). 
  - **Selected: B.** The requester's emphasis was on *which key* is configurable and on feasibility ("check if cmd/alt are possible"), with an explicit `None` default — not on hold semantics. B delivers the configurable keybinding reliably and leaves hold-to-toggle as a documented future extension (see *Open questions resolved*).

- **Which options to expose — full GUI enum (B2) vs TUI-only combo options (B1).**
  - (B1) Expose only reliable key *combos* the TUI already handles (ctrl-s, alt-v, …), no input-layer change. Pros: simplest, no shared-layer risk. Cons: does not mirror the GUI's option list at all (the GUI has only standalone modifiers); the requester asked to mirror the GUI.
  - (B2) Reuse the GUI's `VoiceInputToggleKey` enum (standalone modifiers), with the `KeyCode::Modifier` mapping so they can fire (chosen). Pros: faithful mirror, portable TOML, `None` default. Cons: requires the (contained) input-layer mapping; Super unreliable; Fn infeasible.
  - **Selected: B2.** Mirrors the GUI (the requester's primary ask); the input-layer change is limited to mapping `KeyCode::Modifier(_)` Press→`KeyDown` (no `Release`, no `REPORT_EVENT_TYPES`), which is TUI-only and low-risk. TUI-only combo options are out of scope (future `keybindings.yaml` overrides will cover combos).

- **Setting placement — new TUI group vs reuse AISettings.**
  - Reusing `AISettings` would require a second, TUI-surface instance of the same toml_path on the same group, which the per-surface file generation would emit into both files — ambiguous. 
  - **Selected: a new TUI-surface settings group** (e.g. `TuiVoiceSettings`) with a `voice_input_toggle_key` field of type `VoiceInputToggleKey`, `surface: SettingSurfaces::TUI`, `toml_path: "agents.voice.voice_input_toggle_key"`, `default: None`, `SyncToCloud::Never`, registered in `register_all_settings` (`app/src/settings/init.rs:82` neighborhood). Keeps the TOML path parallel to the GUI while staying TUI-file-only.

- **Binding keystroke representation — string parse vs constructed `Keystroke`.**
  - `EditableBinding::with_key_binding` parses a string via `Keystroke::parse`, which requires a non-modifier key — so a standalone-modifier keystroke cannot be expressed as a parseable string (the GUI hits the same limitation at `ai.rs:221+` and constructs the `Keystroke` directly).
  - **Selected: construct the standalone-modifier `Keystroke` directly** from the enum (mirroring `VoiceInputToggleKey::keystroke()`) and register it on the binding via the keymap's constructed-Keystroke path (or an equivalent builder that accepts a `Keystroke`), so the binding's `Keystroke` matches the `KeyDown` `Keystroke` that `event_conversion` emits for the same `KeyCode::Modifier`. The implementor confirms the exact builder API against `warpui_core::keymap` (see *Open questions resolved*).

*Open questions resolved* (assumptions the implementor/reviewer should confirm; none block the spec):
1. **Hold-to-toggle is out of scope.** Resolved to tap-to-start (B) for reliability and estimate fit; hold-to-toggle (A) is documented as a future extension. If the requester later wants push-to-talk, a follow-up PR enables `REPORT_EVENT_TYPES` + `Release` handling + press/release wiring, gated by `keyboard_enhancement_supported`.
2. **Default `None`; hardcoded `ctrl-s` removed.** Per the requester ("I think it should default to None"). This is a intentional behavior change for users relying on the prior hardcoded `ctrl-s`; document it in the changelog and the PR body.
3. **`Fn` unsupported in the TUI.** No crossterm `KeyCode::Fn` (crossterm `0.29.0`); the Mac Fn key is captured by the OS/winit in the GUI and does not reach the terminal. `Fn` is accepted by the setting (it's a variant of the reused enum) but maps to no active binding. The default-file comment documents this.
4. **`Super` best-effort.** Many terminal emulators do not forward ⌘/Super over the terminal protocol (on Mac, ⌘ is typically captured by Terminal.app/iTerm before reaching the TUI). The variants are exposed and mapped, but may not fire; degrades gracefully.
5. **Left/right distinction.** Assumed crossterm `0.29.0` `KeyCode::Modifier(ModifierKeyCode)` carries left/right variants (e.g. `LeftControl`, `RightControl`) **when the terminal reports them**. The mapping handles whichever side arrives; on terminals that don't distinguish sides, only the reported side fires. Implementor confirms against the pinned crossterm version; if a side variant is unavailable, the binding for that side simply doesn't fire (no crash).
6. **Read-once at startup (no live reload).** The setting is read at binding-registration time (TUI startup), matching the existing TUI settings pattern (`autoupdate.rs:278-280` "read once at TUI startup … next launch"). Edits to the TUI `settings.toml` take effect on the next launch. Live re-registration on settings change is future work. (The GUI applies the key live because it reads it at event time; the TUI's keymap is built once at startup.)
7. **Binding `Keystroke` construction API.** The implementor confirms the exact `warpui_core::keymap` builder for attaching a constructed (non-parseable) standalone-modifier `Keystroke` to an `EditableBinding` (the GUI constructs `Keystroke` directly at `ai.rs:221+`). If no such builder exists today, adding one is in scope for this PR; the binding's `Keystroke` must byte-equal the `KeyDown` `Keystroke` emitted by `event_conversion` for the same modifier.
8. **Milestone "stable" / Priority Medium.** Could not be set via the `scripts/tracker` CLI (no `--milestone`/`--priority` flag on `update-issue`). Flagged to the foreman/requester for manual set on the Linear ticket.

*Risks / blast radius:*
- **Shared input layer.** Mapping `KeyCode::Modifier(_)` to `KeyDown` means bare-modifier presses are no longer dropped. Highest-risk side effect: a bare-modifier `KeyDown` could match a binding the TUI doesn't expect. Mitigation: the only new binding that matches a bare-modifier `KeyDown` is `tui:session:start_voice_input` (and only when the user configured that modifier); chord events arrive as combined `KeyDown`s (key + modifiers) and don't match the standalone-modifier binding. Existing event_conversion + keybindings tests + the cross-surface validators guard this. Criterion #11/#12/#13 verify no collateral damage.
- **Back-compat.** Removing the hardcoded `ctrl-s` default is a user-visible behavior change. Mitigation: default `None` is the explicit request; document in changelog + PR body; the binding name persists for `/voice` and future overrides.
- **Terminal compatibility.** Bare-modifier reporting is terminal-dependent. Mitigation: graceful degradation (criterion #10); Super/Fn documented as unreliable/unsupported.
- **Scope creep toward hold-to-toggle.** Resist adding `REPORT_EVENT_TYPES`/`Release` handling in this PR; it's the boundary that keeps the work at M.
