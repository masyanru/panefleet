# PaneFleet: задачи, шаблоны и связка с трекером

Статус: черновик предложения

Последнее обновление: 2026-08-02

Дополняет [`UI_AND_AGENT_SESSIONS.md`](UI_AND_AGENT_SESSIONS.md). Тот документ описывает
**механизм** — workspace, environment, вкладки, сессии агентов. Этот описывает недостающий
слой **намерения** — над чем идёт работа.

## 1. Проблема

Иерархия PaneFleet целиком названа по механизмам:

```
Workspace → Worktree Environment → Tab → Agent Session
репозиторий      ветка + cwd       окно     процесс
```

Ни один уровень не описывает цель работы. Отсюда три симптома одной причины:

- **Десять вкладок нечитаемы.** Вкладке нечем называться: в её распоряжении только
  `claude`, `zsh` или имя ветки. Ручное переименование — это попытка внести смысл туда,
  где для него не предусмотрено поля. Единственное место, где PaneFleet сам задаёт
  заголовок, — `open_project_session` (`app/src/workspace/view.rs:10187`), и там
  `format!("{project_name} · {session_name}")`, то есть снова механизм.
- **Fleet Dashboard показывает занятость, а не работу.** Его статусы —
  `Restoring / InProgress / Blocked / Failed / Success` — это состояния CLI-процесса.
  Понятия «работа сделана» нет, есть только «агент перестал говорить».
- **Скиллы приходится вызывать руками.** `Agent Definition` отвечает на вопрос
  «как запустить Claude». Вопрос «зачем я его здесь запускаю» не задан ни одному объекту.

## 2. Главное: почти всё уже написано

Прежде чем проектировать новое — три готовых механизма, которые не подключены.

### 2.1 Tab Configs — это и есть шаблон задачи

`app/src/tab_configs/tab_config.rs:144-164` описывает полноценную систему шаблонов:

```rust
struct TabConfig {
    name: String,
    title: Option<String>,                    // Handlebars-шаблон
    color: Option<AnsiColorIdentifier>,
    panes: Vec<TabConfigPaneNode>,            // directory, commands, type, сплиты
    params: HashMap<String, TabConfigParam>,  // text | branch | repo, default
    source_path: Option<PathBuf>,
}
```

Есть параметризация, есть спецпараметр `{{autogenerated_branch_name}}`, есть хелпер
`{{worktree_path_prefix}}`, есть `type = "terminal" | "agent"` на пане, есть произвольные
`commands`. Фича входит в дефолтный набор Cargo (`app/Cargo.toml:680`). Штатный шаблон
`app/resources/tab_configs/default_worktree.toml` уже умеет создать worktree и перейти в него.

**И PaneFleet его обходит стороной**: `create_panefleet_worktree`
(`app/src/workspace/panefleet_worktrees.rs:30`) дёргает `git` напрямую.

Вывод: «шаблон задачи» не надо изобретать — надо провести флоу PaneFleet **через** TabConfig
и добавить туда недостающие поля.

### 2.2 Запуск агента с промптом — недостроенный шов

`PaneFleetAgentDefinition` (`app/src/workspace/panefleet_agents.rs:19-35`) уже содержит:

```rust
prompt_only_args: Vec<String>,
prompt_transport: PaneFleetPromptTransport,   // Argv | Stdin
```

Оба поля персистятся, оба редактируются в Settings
(`app/src/settings_view/panefleet_agents_page.rs:48,60,111-127`) — и **ни одно не читается**
при запуске: `launch_command()` (`panefleet_agents.rs:49-79`) их игнорирует.

Вывод: «запустить агента с начальным промптом» — это не новая фича, а доделка.

### 2.3 Внешнее управление — реализовано и выключено

`crates/local_control/` + `app/src/local_control/` — это готовый loopback HTTP API
(`http://127.0.0.1:<port>/v1/control`, discovery-JSON, Unix-сокет для выдачи одноразовых
credential'ов, проверка peer-UID). Каталог действий (`crates/local_control/src/catalog.rs:169-294`)
весь помечен `Implemented` и включает `tab.create/rename/color.set`, `pane.*`,
`session.list/activate`, `input.insert`, `surface.*`, `file.open`.

В бинарнике `panefleet` он выключен двумя гейтами: `FeatureFlag::WarpControlCli` не добавлен
в `with_additional_features` (`app/src/bin/panefleet.rs:31`), и `LocalControlMode` по умолчанию
`Disabled` (`app/src/settings/local_control.rs:39-46`), причём страница настройки скрыта под
PaneFleet (`app/src/settings_view/mod.rs:1447`).

Вывод: канал для внешнего оркестратора существует; включение — правка на несколько строк.
PaneFleet-специфичных действий в каталоге нет, но каталог — декларативная таблица,
добавление `panefleet.workspace.open` / `panefleet.worktree.create` механическое.

### 2.4 Что действительно надо добавить

Только одно: **объект Task** и его привязка. Всё остальное — соединение существующего.

## 3. Модель

```
Task            намерение: заголовок, внешняя ссылка, шаблон, гейт
 └── Environment  механизм: worktree | directory
      └── Tabs / Agent Sessions
```

Task **не становится ещё одной панелью.** Он становится тем, по чему называется
environment row и вкладки.

Сайдбар начинает читаться так:

```
sentinel
  ● SEC-1802  Onboard Miro audit logs          claude ●··
  ● inc-36884 Databricks PAT triage            claude ✓  codex ●··
  ○ main
```

вместо `main / feature-a / feature-b`. Ветка уезжает во вторичные метаданные.

### 3.1 Кардинальность

**Task ↔ Environment — один к одному.** Это диктуется кодом: идентичность workspace
и environment — это путь на файловой системе (`PaneFleetPersistedWorkspace.path`,
`panefleet_state.rs:48-56`), никакого ID нет. Любая связь «одна задача — несколько
окружений» ломает адресацию по пути.

Задача, трогающая два репозитория, выражается двумя связанными Task
(`related: Vec<TaskId>`), а не одной задачей с двумя окружениями.

### 3.2 Не всякая задача требует worktree

Триаж инцидента не нуждается в git-ветке — ему нужна директория. Поэтому
`Environment.kind ∈ { worktree, directory }`. Это обобщение того, что уже есть в спеке
(«обычная не-Git папка остаётся одним невложенным workspace»), возведённое в первый класс.

### 3.3 Где хранить

`PaneFleetWorkspaceSource` (`panefleet_state.rs:60-69`) — закрытый enum, и он был
**намеренно сужен** (коммит `eaf609cb3 constrain Fleet workspace metadata`). Не расширять его.

Вместо этого — отдельный версионированный файл `panefleet-tasks.json` в `state_dir()`,
по тем же правилам, что и остальные пять (атомарная запись через tmp+rename,
`load_or_default`, игнор файлов более новой версии), и поле рядом с
`panefleet_workspace_sources` (`view.rs:1119`):

```rust
panefleet_tasks: HashMap<PathBuf, TaskBinding>,
```

```rust
struct TaskBinding {
    id: String,                       // локальный: t-0042
    title: String,
    external: Option<ExternalRef>,    // { provider, key, url }
    template: Option<String>,         // имя TabConfig
    state: TaskState,
    done_check: Option<Vec<String>>,  // argv
    schedule: Option<TaskSchedule>,   // §6.1
    related: Vec<String>,
}
```

Секреты и токены в файл не попадают — как и во все остальные PaneFleet JSON.

### 3.5 Вкладка — это задача, панели — это агенты

Вкладка перестаёт быть «одним агентом». Одна задача = одна вкладка = до четырёх панелей.
Десять вкладок превращаются в три. Заголовок вкладки — `SEC-1802 · Onboard Miro audit logs`
вместо `sentinel · claude` (одна строка в `view.rs:10187`).

Четвёртая панель в примере — не ещё один шелл, а `done_check` в режиме watch. Так вторая
ось состояния (§4) перестаёт быть абстракцией на доске и получает место в рабочем окне.

**Сплиты уже работают.** `CustomAction::SplitPaneRight/Left/Down/Up` есть в меню
(`app_menus.rs:524-527`) и не гейтятся флагом `PaneFleetWorkbench`; `PaneGroup` —
рекурсивное дерево (`PaneNodeSnapshot::Branch { direction, children } | Leaf`,
`app_state.rs:99-102`). Переключение окружений layout переживает: `PaneFleetProjectTabState`
держит живые `tab_groups` в памяти.

**Ломается только перезапуск приложения**, по двум причинам:

1. `restore_panefleet_state` (`view.rs:9840`) пересоздаёт каждую вкладку как
   `PanesLayout::SingleTerminal`, хотя рядом, в нативном пути Warp (`view.rs:4786`),
   используется `PanesLayout::Snapshot` с полным деревом панелей.
2. `PaneFleetPersistedTab.agent_session` (`panefleet_state.rs:83-87`) — единственное число,
   а `panefleet_tab_sessions` ключуется по id **pane group**, то есть по вкладке. Даже
   с восстановленным layout из четырёх агентов вернётся один.

Что нужно:

```rust
struct PaneFleetPersistedTab {
    title: Option<String>,
    task_id: Option<String>,
    layout: Option<PaneNodeSnapshot>,              // вместо неявного SingleTerminal
    agent_sessions: Vec<PaneFleetPersistedPaneSession>,
}

struct PaneFleetPersistedPaneSession {
    pane_path: Vec<u8>,                            // путь в дереве, а не EntityId
    agent: CLIAgent,
    provider_session_id: Option<String>,
    role: Option<String>,                          // build | skeptic | gate | shell
}
```

Ключ по `EntityId` для персистенса не годится — он процесс-локальный. Нужен устойчивый адрес
панели внутри дерева (индексы ветвлений), совпадающий с тем, как `PaneNodeSnapshot`
восстанавливает layout.

**Ограничение, которое обязано попасть в шаблон.** Codex хранит подписочные токены в общем
`~/.codex/auth.json` и переписывает их при обновлении; документация OpenAI требует один раннер
на файл и запрещает параллельные — второй процесс, обновив токен, инвалидирует первый.
Значит `AgentDefinition` нужен признак **single-instance-per-machine**, и шаблон задачи должен
отказываться ставить две панели Codex (в том числе в разных задачах одновременно).
Для Claude и OpenCode такого ограничения нет.

**Лист новой задачи.** Шаблон выбирается первым и задаёт всё остальное.

```text
┌──────────────────────────────────────────────────────────┐
│ Новая задача                            из Jira SEC-1802 │
├──────────────────────────────────────────────────────────┤
│ ЗАГОЛОВОК     Onboard Miro audit logs                    │
│ ШАБЛОН        connector-onboarding                     ▾ │
│ ОКРУЖЕНИЕ     worktree · from main                     ▾ │

│ АГЕНТЫ        [x] Claude    /sentinel-data-connector miro│

│ ГОТОВО, ЕСЛИ  ./deployment/deploy.sh --dry-run           │
├──────────────────────────────────────────────────────────┤
│ Отмена     создаст worktree, 3 вкладки          Создать  │
│            и отправит промпт в Claude                    │
```

**Fleet Dashboard как очередь внимания.** Колонка оправдана, только если меняет то, что
человек делает дальше. По этому тесту `Working` и `Done` колонок не заслуживают — они не
требуют ничего и уезжают в полосу счётчиков и в сворачиваемый ящик.

```text

├ ВЫТЯНУТЬ 2 ─────────┬ РАЗБЛОКИРОВАТЬ 2 ──────┬ АВТОРИЗОВАТЬ 6 ─────────────┤

│ SEC-1810            │ ждёт 6m                │ └закрыть инцидент?        ┘ │
│ Onboard Figma       │                        │ claude + codex · 21m        │
│ из jira             │ inc-36901              │                             │
│                     │ ┌done_check провален ┐ │ ┌ +5 таких же —           ┐ │
│                     │ └нет observation     ┘ │ └ просмотреть пачкой      ┘ │
│                     │ прогон 2 из 3          │                             │
├─────────────────────┴────────────────────────┴─────────────────────────────┤
│ ▾ DONE · за сутки 12   SEC-1754 · inc-36877 · PF-11 · inc-36871 · ещё 7    │
└────────────────────────────────────────────────────────────────────────────┘
```

Три колонки — это три типа действия, а не три стадии процесса:

- **Вытянуть** — решить, что запустить. Существует, пока задачи вытягиваются вручную;
  при полностью автоматическом запуске вырождается.
- **Разблокировать** — работа **не** сделана: агент задал вопрос или `done_check` провалился.
  Думать надо поштучно.
- **Авторизовать** — работа сделана и гейт пройден, предлагается **необратимое** действие.
  Это **пакетируется**: шесть готовых к закрытию инцидентов просматриваются одним заходом,
  как это уже делает `close-bulk.sh` с одним подтверждением на пачку.

Поштучное мышление против пакетного — разные режимы, поэтому две колонки, а не одна.
Карточка в «Авторизовать» показывает **основание** для решения, а не просто «готово».

## 4. Две оси состояния

```
процесс (есть):  Restoring · InProgress · Blocked · Failed · Success   ← про CLI
задача (нужно):  Queued · Working · NeedsReview · AwaitingAck · Done   ← про работу
```

Мост между ними — `done_check`: argv, который PaneFleet запускает в cwd окружения после
перехода turn'а в `Success`, и смотрит на код возврата. Ноль → `Done`, иначе → `NeedsReview`.

Дёшево до неприличия, а разница принципиальная: «Claude замолчал» против «работа прошла
проверку». Для кода это `cargo test`, для расследования — `selfcheck.sh <номер>`.

Правило: **`Done` недостижим без прохождения `done_check`.** Ручной перевод возможен,
но помечается как ручной.

Состояние задачи и колонка доски — не одно и то же: `Working` и `Done` являются состояниями,
но колонок не получают, потому что не требуют действия (§3.4).

## 5. Источники и приёмники задач

Не тащить в приложение SDK трекеров. Два тонких шва, оба — внешние команды:

- **Task source** — команда, печатающая JSON `[{ id, title, url, template? }]`. Тогда Jira
  по JQL, `queue.sh` с инцидентами Sentinel и GitHub issues — это одна и та же сущность,
  три разных скрипта. Колонка `Queued` наполняется сама.
- **Task sink** — команда на переходе состояния: `on_done`, `on_blocked`.

PaneFleet остаётся вендор-нейтральным, специфика живёт снаружи.

**Прецедент для deeplink уже есть**: `warp://linear/work?prompt=…` (`app/src/linear.rs`,
обработчик `view.rs:21212-21261`) разбирает промпт из query-строки, открывает вкладку
и стартует агента. Jira-хост клонируется с него один в один.

Но сперва придётся починить баг (см. §7.1).

## 6. Fleet Dashboard

Не строить рядом вторую доску. Fleet Dashboard уже полноэкранная сетка карточек
(`render_panefleet_fleet_dashboard`, `view.rs:24307`). Перегруппировать её в очередь
внимания (§3.4), оставив workspace как фильтр. Это переиспользование поверхности,
а не новый экран — иначе сайдбар и доска начнут дублировать друг друга.

Карточка показывает заголовок Task, а не `display_title()` последнего промпта
(`view.rs:3993`) — сейчас там текст пользовательского ввода, обрезанный до 96 символов.

## 6.1 Повторяющиеся задачи

Длинный цикл нельзя делать одной длинной сессией: контекст дорастает до компакта и агент
дрейфует, одна сессия держит окно рейт-лимита, ошибка в середине не оставляет чекпоинта.
Его надо делать **многими короткими прогонами**, а состояние между ними держать **в файлах,
а не в истории разговора**.

Это уже работает в `~/ops/sentinel/agent-triage-job/`: launchd каждые 15 минут → `queue.sh`
→ по одному `claude -p` на инцидент → состояние в `triaged.tsv` → `MAX_ATTEMPTS` и poison.
Шедулер PaneFleet обобщает этот паттерн, а не изобретает «оставить агента крутиться».

`schedule` — свойство задачи, а не колонка:

```rust
struct TaskSchedule {
    cadence: String,            // "15m" | "daily 03:00" | "weekly mon 09:00"
    scope: ScheduleScope,       // WhileOpen | System
    session: SessionPolicy,     // Fresh (по умолчанию) | Resume
    max_turns: Option<u32>,
    max_budget_usd: Option<f32>,
    on_overlap: OverlapPolicy,  // Skip | Queue
    park_after_failures: u32,   // аналог MAX_ATTEMPTS
}
```

Обязательные умолчания и почему:

- **`session: Fresh`** — `--resume` растит контекст от прогона к прогону, и именно это ломает
  длинные циклы. Состояние переносится файлами, которые пишет сам прогон.
- **`on_overlap: Skip`** — не запускать, если прошлый прогон ещё идёт.
- **`park_after_failures: 3`** — после трёх неудач подряд расписание останавливается
  и показывает последнюю ошибку. Молча долбиться нельзя.
- **`max_turns` / `max_budget_usd`** — у Claude Code это `--max-turns` и `--max-budget-usd`,
  оба поддерживаются в headless-режиме.

**На доске у запланированной задачи своей колонки нет.** Она живёт в списке расписаний
и всплывает в «Разблокировать» или «Авторизовать», только когда прогон что-то произвёл.
Иначе доска забьётся задачами, которые просто тикают.

**Два разных механизма, показанные разными метками:**

- `while open` — таймер внутри приложения. Тикает, только пока PaneFleet запущен. Этого
  достаточно для «проверяй, пока я работаю», и это просто: инфраструктура таймеров уже есть
  (проверка релизов раз в 24 ч, `panefleet_update.rs:16-19`).
- `system` — расписание отдаётся launchd, прогон случается без приложения.

Прятать разницу за одной абстракцией нельзя: пользователь должен понимать, случится ли
ночной прогон при закрытом ноутбуке.

## 7. Найденное в коде, что стоит исправить отдельно

### 7.1 Deeplink'и не работают

Info.plist регистрирует схему `panefleet://` (`app/src/bin/panefleet.rs:64-65`), а
`validate_custom_uri` (`app/src/uri/mod.rs:1676-1690`) сравнивает со значением
`ChannelState::url_scheme()`, которое для `Channel::Oss` возвращает `"warposs"`
(`crates/warp_core/src/channel/state.rs:396-406`). Схема зарегистрирована в системе
и отвергается приложением. **Весь механизм deeplink'ов сейчас мёртв.**

### 7.2 Имена скиллов до приложения не доходят — их не шлёт плагин

**Проверено 2026-08-02.** Гипотеза была наполовину верна: расширять протокол на стороне
Rust действительно не нужно, но и «бесплатно» не получится — данные теряются в плагине.

Цепочка целиком:

| Звено | Что есть |
|---|---|
| hook input Claude Code | Имена **есть**: `Skill` → `input:{"skill":"claude-api",…}`, `Agent` → `"subagent_type":"Explore"` (подтверждено по транскриптам в `~/.claude/projects`) |
| `warp@claude-code-warp` 2.2.0, `scripts/on-post-tool-use.sh:19-22` | Шлёт **только** `tool_name`; `tool_input` не форвардит |
| `event/v1.rs:28-33` | Поле `tool_input` парсится, но извлекает лишь `command`/`file_path` |
| `cli_agent_sessions/mod.rs:464-476` | `ToolUsed` эмитится **исключительно** из `tool_complete` |
| `panefleet_claude.rs:11-12` | Получает голый `tool_name` — данные не отбрасываются, их просто нет |

`tool_input` шлёт единственный хук — `on-permission-request.sh:20,37`, и это состояние
затирается в `clear_permission_scoped_state()` (`mod.rs:177-181`) при выходе из permission-флоу.

Что нужно, чтобы таймлайн получил имена:

1. `on-post-tool-use.sh` должен форвардить **два ключа**, а не весь `tool_input`, — тогда
   приватностный инвариант («не храним prompt, response, tool input») сохраняется.
   Скрипт живёт в **чужом репозитории** `warpdotdev/claude-code-warp`, версия запинена
   в `plugin_manager/claude.rs:19-24`. Значит либо PR апстрим, либо свой marketplace-форк

2. Вайтлист `skill` / `subagent_type` в `v1.rs`, проброс через `ToolUsed` и
   `classify_claude_tool`. Это правка на десяток строк и от пункта 1 не зависит по коду,
   но без него бесполезна.

**Сделано 2026-08-03.** Rust-сторона готова: `v1.rs` вайтлистит ровно два ключа,
`CLIAgentEventPayload.tool_capability` несёт имя, `ToolUsed` его пробрасывает,
`classify_claude_tool` подставляет в `Skill`/`Subagent`. Плагины, которые имя не шлют,
дают безымянную запись — прежнее поведение. Имя ограничено теми же 80 символами, что и
имя инструмента: оно приходит из плагина и доверять ему нельзя.

Патч для плагина — `specs/panefleet/claude-code-warp-tool-capability.patch`, применяется

`PANEFLEET_PROJECT_LIMIT = 6`, `PANEFLEET_ENVIRONMENT_LIMIT = 12`
(`app/src/workspace/left_panel.rs:98-99`). Если задачи становятся environment-строками,

### 7.4 Прочее

- `panefleet_agent_turn_started_at` живёт только в памяти — время работы сбрасывается при рестарте.

## 8. План

Каждый пункт — «что · где · готово, когда». Этапы упорядочены по зависимостям: **P0**
самодостаточен и уже снимает основную боль; **P1** не зависит от P0, кроме именования;

### Известные дефекты, оставленные сознательно

Ревью ветки P0/P1 (2026-08-02, восемь углов) дало десять находок; девять — в коде
того же дня. Пять исправлено сразу, четыре — вторым заходом. Осталось следующее,
в порядке ожидаемой боли.

- **Состояние восстановления — одна ячейка на вкладку.** `panefleet_agent_restore_states`
  ключуется по pane group, а агентов во вкладке теперь может быть несколько: состояние
  одного затирает другого, и событие одного агента снимает или проваливает состояние
  соседа. Пере-ключение трогает 14 мест и требует заодно сделать баннер восстановления
  по-панельным — сейчас он показывает одно состояние на вкладку. Дефект про точность
  индикатора: сессии и `provider_session_id` не страдают.
- **Adopt сопоставляет вкладки по количеству.** `adopt_restored_tabs` сравнивает только
  `len()` и дальше связывает вкладки позиционно. Перетащил вкладку перед перезапуском —
  `claude --resume` уйдёт в чужой терминал. Устойчивый адрес панели для этого уже есть
  (`session_uuid`), не хватает такого же для вкладки.
- **`panefleet-tasks.json` не чистится.** Привязка снимается только через «Clear Task» и
  при удалении worktree из меню. Worktree, удалённый `git worktree remove` из терминала,
  или стёртая папка остаются в файле навсегда; путь, переиспользованный новым окружением,
  унаследует чужой заголовок и состояние.
- **Изоляция от Warp OSS сделана наполовину.** Worktree ушли в `~/.panefleet/worktrees`,
  но `panefleet-tasks.json`, `panefleet-workspaces.json`, события и настройки по-прежнему
  лежат в общем `~/.warp-oss`. Настоящее место правки — отображение канала в каталог
  (`macos_config_dir_name_for`), которое игнорирует уже объявленный AppId
  `dev.panefleet.PaneFleet`.
- **Лишняя работа на горячих путях.** `PaneFleetTaskStore::labels()` строит новую карту
  на каждый кадр дашборда и на каждое событие агента; `panefleet_pane_uuid_for_terminal_view`
  обходит все вкладки всех проектов, хотя pane group уже вычислен строкой выше.
- **Агент в окне создания зашит как Claude.** Выбора нет; при выключенном в лаунчере
  Claude команда соберётся из фолбэка на несуществующий бинарь.
